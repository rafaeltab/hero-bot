# Mutation efficiency: wallpaperdb and hero-bot

Research snapshot: 2026-11-14 UTC. Read-only source/Actions inspection through `gh`; no mutation benchmarks run. Hero-bot source: `439aed8a77735024be4ddd7971c6f8f0eb06e626` (shared checkout); wallpaperdb main: `5e4a07c4648c0d93006626cabc089d623e759e75`. Run observations below identify their own revisions. **Verified** describes inspected code or reports; **proposed** describes unmeasured changes.

## Why eight long shards? Verified

- The workflow explicitly schedules eight advisory jobs, each with a **240-minute ceiling**, not a one-hour target. Its history note says four 20-minute shards could not finish the notification scope. The documented inventory is 2,807 mutants, distributed 401/440/398/363/211/221/410/363. Eight shards preserve scope rather than sampling it. [Workflow lines 9–20][h-workflow]; [validation lines 27–50][h-validation].
- The expensive inner loop is `pnpm build && pnpm test` **for every mutant**: command runner, coverage analysis off, concurrency 1, `disableBail: true`. In this app build means `tsc`, and test means `vitest run`. Changed-line scope already exists; the missing optimization is safe selection of tests within that scope. [Execution lines 43–69][h-execution]; [app scripts lines 5–12][h-package]; [planning lines 54–84][h-planning].
- This fallback has a correctness reason: tests launch compiled child processes, which an in-process mutation coverage map cannot safely associate with individual tests. Ordinary V8 subprocess coverage (`autoAttachSubprocess`) does not establish Stryker per-test activation/selection. The repository records a real fixture where native per-test mode labels subprocess-only mutants `NoCoverage`, while full-suite mode kills them. [Process test lines 1–20][h-process]; [Vitest lines 9–20][h-vitest]; [validation lines 66–83][h-validation].
- Shards balance **changed line counts of indivisible original ranges**, not mutant counts or execution cost. Whole ranges avoid losing multiline mutations at arbitrary split boundaries, but produce uneven loads. CI requests neither per-test selection nor incremental reuse; CLI defaults are full-suite/fresh and incremental is rejected in full-suite mode. [Planning lines 88–118][h-planning]; [CLI lines 6–28][h-cli]; [workflow lines 47–52][h-workflow].

## What wallpaperdb does differently — verified mechanisms and limits

| Mechanism                        | Inspected behavior                                                                                                                                                                                                                                                                                                                                                                         | Caveat for hero-bot                                                                                                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native coverage-guided execution | Stage runner uses Vitest `perTest` coverage and incremental results, still with concurrency 1. Gateway separates unit tests from a Redis integration project that imports instrumented code in-process. [Stage lines 81–108][w-stage]; [unit config lines 4–21][w-unit]; [Redis config lines 4–22][w-integration].                                                                         | Speed comes from reducing per-mutant work, not more Stryker workers. The native runner cannot simply replace hero-bot’s subprocess fallback.                              |
| Unit-first integration gating    | Integration gate contains only unit `Survived`/`NoCoverage` identities; coordinator skips integration without eligible candidates. Reporter defers other mutants while retaining native coverage-selected plans. [Stage lines 81–88][w-stage]; [coordinator lines 378–423][w-coordinator]; [reporter lines 95–119][w-reporter].                                                            | Requires compatible mutant identities, trustworthy unit evidence and explicit handling of pending/error/static results.                                                   |
| Bounded, resumable work          | One mutation job; PR aggregate execution budget 900 seconds, default 120-second stage quantum, nightly all-scope schedule. It saves cumulative checkpoints and explicitly turns an `incomplete` exit into an advisory warning/success. [Workflow lines 3–29, 49–64, 150–170][w-workflow].                                                                                                  | This caps feedback cost; it does **not** make a complete analysis faster. A green job can be incomplete.                                                                  |
| Controlled incremental identity  | Compatibility tracks workspace dependencies, tooling/configuration, declared environment keys and runtime/tool versions separately from source/test inputs. Trusted remote checkpoint candidates are successful default-branch schedule/dispatch/push runs; PR workflow runs offline. [State lines 92–218][w-state]; [remote lines 16–62][w-remote]; [workflow lines 124–128][w-workflow]. | Cache reuse needs invalidation and trust boundaries. The two recent runs examined below reported zero reuse in their visited stages.                                      |
| Reused integration fixture       | Redis pilot reuses an owned container, checks leaked clients, synchronously flushes and verifies empty state before another mutant; optional isolated mode recreates it. Reset failure aborts execution externally. [Fixture lines 186–222][w-fixture]; [setup lines 1–24][w-setup].                                                                                                       | This is a Redis-specific pilot, not proof that sharing PostgreSQL connections/schema/process state is safe. Hero-bot already provisions one PostgreSQL service per shard. |
| Explicit support inventory       | Most app entries enable unit mutation only; gateway adds bounded Redis integration. Subprocess, database/container and browser gaps have explicit exclusions/limitations. [Inventory lines 5–101, 103–134][w-inventory].                                                                                                                                                                   | wallpaperdb is not evidence of equivalent full integration coverage at lower cost.                                                                                        |

Additional portability cost: wallpaperdb carries a Stryker Vitest 10.0.0 patch affecting test identifiers, isolation and failure handling. Hero-bot pins Stryker 10.1.1; copying the patch without version-specific validation would be unjustified. [Patch lines 1–80][w-patch]; [hero-bot validation lines 92–104][h-validation].

## Suggested improvements — proposals, not implemented or measured

1. **Reduce the inner loop first.** Introduce a qualified in-process mutation stage for domain/application behavior and adapter contracts, retaining compiled process tests as a separately reported fallback. Pilot a small existing scope and prove identical mutant identities plus known kills (including static initialization) before migration. Then apply unit-first survivor/NoCoverage integration gating where evidence is compatible. This follows wallpaperdb’s useful architecture without silently dropping hero-bot integration evidence.
2. **Measure costs before changing shard count.** Record compile, dry-run, selected-test, mutation execution and fixture-reset time separately. Balance whole ranges using mutant inventory and historical execution cost rather than line counts; preserve exact scope/completion checks. More shards mainly lower elapsed time while repeating setup and leaving total build/test work intact.
3. **Add checkpoint continuation after test selection is sound.** Persist completed mutant evidence with configuration/tool/test/environment invalidation; begin with same-input retries. Hero-bot’s current whole-repository fingerprint and base/range-bound key are conservative and CI does not restore caches, so merely adding an Actions cache cannot provide wallpaperdb-style cross-edit reuse. [Cache lines 6–46][h-cache]; [CLI lines 22–25][h-cli].
4. **Make bounded PR feedback an explicit policy choice.** A short PR budget plus cumulative nightly/manual continuation can control cost, but must report pending/incomplete status and retain a path to complete the full scope. Current ADR 0003 and validation require sound fallback and honest completion accounting; adopt that reporting contract before copying wallpaperdb’s green-on-incomplete behavior. [ADR 0003][h-adr]; [validation lines 38–50][h-validation].
5. **Treat smaller optimizations as secondary.** Centralizing `mutation:verify` could remove eight repeated fixture runs, but measured overhead is tens of seconds versus hours of analysis. Investigate early test failure exit and modest concurrency only with failure/fixture-isolation checks. Do not substitute `vitest.related`, silently ignore `NoCoverage`, remove subprocess tests, or increase timeouts as the main efficiency fix.
